The --mds-* names on this page are documentation. They are never shipped.

--mds-* is core's design-system namespace: Moodle 5.2 ships theme/boost/scss/design-system/ defining $mds-*, 5.1 has no such directory, and 5.3 LTS brings MDS React. Naming core's palette here is how this kit stays legible against core's own vocabulary, and it is legitimate in documentation. Declaring those names in shipped CSS is not: it squats a namespace core is actively expanding, and on :root it does so globally. The plugin's stylesheet therefore declares only --local-dimensions-*. If a future reader is tempted to "finish the job" by moving this block into styles.css, that is the mistake this paragraph exists to prevent. (The plugin's own --mds-* motion tokens were renamed away for exactly this reason on 2026-08-06; see the comment at the head of styles.css.)

What styles.css ships — 34 colour tokens on bare :root
The plugin does not own a palette; it delegates to core's and names only the roles it needs. 30 of the 34 are written var(--bs-NEW, var(--BS4-OLD, #literal)). Measured on the running stacks: Moodle 4.5 declares none of these --bs-* names and Moodle 5.1/5.2 declare none of the Bootstrap 4 legacy names, so exactly one rung resolves per branch and the literal is a safety net. Because Moodle 5.1/5.2 already compile a complete [data-bs-theme="dark"] token block, those 30 are dark-correct with no dark rule at all — the plugin's card face is --bs-body-bg, the same value the page background uses, so the two cannot disagree. Only three tokens carry a plugin-authored dark value. The dark column below is core's own measured output, read from the compiled Boost sheet on m502.

The three marked plugin-owned are the entire dark rule. They are the whole contents of :root[data-bs-theme="dark"], and core has no equivalent for any of them: --bs-box-shadow is a whole shadow rather than a colour and is absent from the dark block, no core token is a translucent surface, and no single star hue clears 3:1 on both #fff and #343a40 (--bs-warning is 1.95:1 on white). That bound is what makes it impossible for this plugin to paint a dark surface on a light page: even if the rule fired on a branch with no dark palette, the worst outcome is a deeper shadow, a darker veil and a brighter star. colour_tokens_test::test_dark_activation_block_assigns_only_plugin_owned_tokens fails the build if a fourth name joins them.
Moodle 4.5 differs from the light column in three places only, because its literal is the last rung rather than core's compiled light value: ink-muted is a flat #495057, ink-faint a flat #6a737b, and ink-strong / focus-ring are #343a40 rather than #000 (still 11.5:1 on surface). Every other token's 4.5 literal equals the 5.x light value shown, by construction.
Two names on this page are deliberately not tokens. --dimension-custombgcolor and --dimension-customtextcolor are the cross-plugin transport for admin instance data — a colour a site chose. They are read by the surfaces an admin has painted and are never declared in the token block and never re-pointed in the dark rule, so a site's colour stays its colour in both modes and only the neutrals around the island adapt. The hero photo overlays and the glass chips composited over an admin colour stay literals for the same reason: they are relative to the admin's colour, not to the page.

Secondary Danger Danger hover
Focus is an outline, not a halo — and it is no longer the brand colour. The converged pattern is outline: 2px solid var(--local-dimensions-focus-ring) with outline-offset, written by 49 rules; the offset is 2px outside (36×) and -2px inside (19×) when the target touches its container's edge. The ring chains --bs-emphasis-color, not --bs-focus-ring-color: core's own focus colour does not flip — measured live it is the same rgba(15, 108, 191, .25) in both modes, 1.02:1 against the dark page — and a 3:1 obligation cannot be delegated to a colour the site owner picks either (--bs-link-color is 2.33:1 on that theme's dark card). The emphasis extreme flips and is theme-independent: 21.0 / 19.9 / 17.7 light, 16.2 / 13.7 / 11.5 dark, 11.5 / 10.9 / 9.7 on 4.5, against surface / surface-alt / surface-inset. Two offences are now build failures rather than conventions: a focus rule that switches the outline off without drawing another, and one whose only visible signal is a box-shadow — Windows High Contrast Mode renders no box-shadow at all and does not restore an author's outline: none. The one currentcolor ring is on a branded island, where the ground is the admin's colour in both modes.
secondary is the only unsaturated fill — grey with adaptive text — so it needs a dark variant, and in the shipped stylesheet it gets one for free by being surface-inset + ink rather than a fill of its own. primary and danger are saturated fills with fixed white text, the same reading in both schemes. What the plugin actually ships is narrower than this row suggests: exactly one solid brand fill, brand-fill, and the only text permitted on it, on-brand-fill. That pairing is .btn-primary's own contract and nothing more — --bs-primary does not flip (1.10:1 as text on the dark page), so the brand solid is never an ink, never a border that carries state and never a focus ring. The tone solids (--bs-success and friends) are barred as indicators for the same reason: none of them flip, and their failures fall on disjoint sets per branch. Meaning rides -ink / -tint / -edge, which is what core's own .alert-* is built from, so a plugin chip and a core alert match on the same page. The hub still draws no danger button of its own; it uses Boost's .btn-outline-danger.
Feedback — status tints (text at stop 800)
info · cyan success · green warning · yellow danger · red
These pairs are now the plugin's only status vocabulary, hub and learner views alike. The two dialects this note used to describe have merged: the hub's link badges and the learner views' evidence and status pills all read the same six -ink / -tint / -edge triples, and the learner-side Bootstrap tints they used to write by hand (#d1e7dd/#0f5132, #fff3cd/#664d03, #f8d7da/#842029) return zero hits. The info/cyan family, which had no occurrence at all, now carries the evidence rule chip — it replaced an orphan purple that belonged to no family. The contrast checker no longer inverts itself. It used to carry its own @media (prefers-color-scheme: dark) rules, which flipped that one panel from the OS preference while the rest of the Moodle page stayed light: a plugin surface dark inside a light page, which is the exact defect the whole token design exists to prevent. Those rules are gone, and the panel now follows the host like everything else.

Motion — the four tokens styles.css :root declares
fast 150ms · hover, focus, colour base 250ms · layout, tab indicator flash 1500ms · in-place confirmation
Hover the first two to feel 150ms against 250ms; flash does not transition — the JS is what fires it. A single easing --local-dimensions-motion-ease = cubic-bezier(0.4,0,0.2,1) (Material standard). fast matches Bootstrap's .15s. Under prefers-reduced-motion both transitions disappear — here in the card and in the shipped code too, where every rule that uses the tokens carries its own clause (e.g. styles.css:7267-7271).

What the code actually declares and consumes
  • styles.css declares two :root blocks: the five motion and loading properties (--local-dimensions-motion-fast, -motion-base, -motion-flash, -motion-ease, -loading-min-height) and the 34 colour tokens shown at the top of this page, plus one activation rule, :root[data-bs-theme="dark"], carrying three declarations. The old claim on this line — "exactly five custom properties, and the shipped CSS writes literals" — has been false since the colour tokens landed.
  • The --mds-* names elsewhere on this page remain the kit's vocabulary for core's palette, and are documentation only: see the warning at the top. The shipped stylesheet declares --local-dimensions-* and nothing else.
  • Verified consumers: --local-dimensions-motion-fast on the modal header's chip (:4944), --local-dimensions-motion-base on the tab indicator (:7244), --local-dimensions-loading-min-height on the busy cover (:4030).
  • --local-dimensions-motion-flash is read by JS, not by CSS: central/flash.js:43 does getComputedStyle(el).getPropertyValue('--local-dimensions-motion-flash') and passes the duration to the WAAPI, with a 1500 fallback. The helper is a single one and replaced ten inline copies across six hub modules; today it is imported by structure, plans, competency_links, enrol_methods, roles_manager and related_competencies.
  • Adoption scope for motion is still new or reworked surfaces only. Colour is no longer opt-in: the retro-tokenisation happened, the divergence this line used to defend is closed, and a colour literal outside the token block now fails the build rather than being tolerated as an un-migrated surface.
  • Semantic --mds-* naming (primitive→semantic): when the React MDS lands (Moodle 5.3 LTS), the migration becomes a rename, not a redesign.
