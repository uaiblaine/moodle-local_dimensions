The boundary of the sticky-footer rule (settled 2026-07-14). The "never a per-row kebab" rule governs the CRUD of the tab's own entity (framework / structure node / template) — which goes to the sticky footer because that is what launches the modals. The actions on competencies inside a plan's list are a nested list and legitimately use a kebab (plans.mustache:422-462): this tab's sticky footer is already occupied by the selected template's actions. This kebab is correct — do not "fix" it.
The strongest proof is the shared openForm. The kebab's edit-competency (plans.mustache:431-434) and the footer's edit-template (:465-468) call the same function — openForm (plans.js:201-209, whose new ModalForm sits at :201) — which the header's new-template calls too. All three coexist because openForm is parameterised by formclass: the kebab passes COMPETENCY_FORM_CLASS (plans.js:731-737), the footer and the header pass FORM_CLASS (:721-727, :714-720). Different entities, same mechanism — which is why kebab and footer coexist without ambiguity.
And the footer is still dominant — measured numbers. The hub has 17 modal construction sites (4 new ModalForm + 13 Modal*.create, all under amd/src/central/). The footer reaches 10 directly, is the only door to 7, and 8 depend on it (the 7 plus enrol_methods, which only exists inside the participants modal). The other 3 — the framework, competency and template forms — have a parallel door in the header, but the footer button is the only way to act on the selected row. That is 7 with no other door, not 10.
