Retired — the pane's four "Refresh" buttons (7d69197, 2026-07-18). They were four data-action="enrol-refresh" buttons (one in each of the three alerts + one on the filters bar), the pane's only refresh affordance; they left together with their click handler. A grep -rn 'enrol-refresh' templates/ amd/src/ returns nothing. The ID ENROL-REFRESH is recorded here and in the map only for whoever comes looking for it — there is no corresponding control.
Where this pane's refresh lives. In the modal header: the mount (enrol_methods.js:1082-1112) returns {refresh: () => init(state)} (:1111) and the host wires it with attachRefresh (participants_manager.js:232, callback refreshActiveTab at :213-229). The busy discipline the four extinct buttons lacked — clicking twice fired two concurrent inits — exists in the replacement: modal_refresh.js:70-84 disables the button (:74), puts fa-spin on the icon (:75) and clears both in a finally (:80-83). The chip is the same one as the other header controls (styles.css:4929-4945, disabled at :4962-4964) and the label is core's string getString('refresh') (modal_refresh.js:63) — no new string.
Which failures the 4th gate covers — and which it does not. The try/catch in init (enrol_methods.js:917-944) wraps only the first load (the Promise.all at :918-934, list_template_cohorts + list_enrol_competencies) — the failure that rejected before any region was revealed and left the pane blind. The others do not need it: ENROL-EMPTY/ENROL-DISABLED are paths where init succeeded and revealed an alert, and the late failure (loadCompetencies, :473, called again by reload at :788-794 and by the "Load more" buttons) already happens with main.hidden = false done (:967), so the pane stays in view and usable. The late one was left as it was, on purpose.
The mount latch belongs to the host, and this tab is the deliberate exception. startMount (participants_manager.js:198-210) claims the latch synchronously and releases it in the .catch (:207), so re-clicking the tab re-mounts — but enrol delegates its listeners on the container element itself (wireEvents, enrol_methods.js:1103), which replaceNodeContents does not discard, so re-mounting would stack listeners. That is why the first load's failure is swallowed into a toast (:1108, comment at :1104-1107): the mount resolves, the latch stays true on purpose and coming back to the tab does not retry. Recovery is the header's refresh — and that is exactly why the 4th gate has to exist: with no visible region, a blank pane would have no way of being recovered in place. A related detail: the accordion's latch (data-loaded) is reverted on error (:573), so it recovers by itself. The full mechanics of the latch are in maps/mod-participants.md (PART-LATCH).
This pane does not use reloadPane, and it is no exception to anything: it is a modal pane, not a core/dynamic_tabs tab pane — reloadPane would not reach it. Measured precision, because this is easy to get wrong: reloadPane is defined at tabs.js:69 and has 24 calls across 5 modules — structure 9, frameworks 6, plans 6, context 2, competency_browser 1. (A grep -rn reloadPane amd/src/ returns 36 lines: the 24 calls + the definition + 5 imports + 6 comments.) Two of those 24 are the contextbar's data-action="refresh" button, which means: there is a UI control that fires reloadPane — it just is not this pane.
