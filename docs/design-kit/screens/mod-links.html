Empty state: "No courses linked." MOD.LINKS-EMPTY · competency_links.mustache:47-49 — the condition comes from the server: the message appears with state.total === 0, where total is the full link count the WS returns (get_competency_links.php:126-132, deliberately not narrowed by the exclusion). "Load more" is the same function's counterpart: it shows while there are fewer cards on screen than total. Both lines live in refreshListState (js:437-440), called by every transition — load (js:487), add (js:761) and removal (js:647).
There is no offset cursor. Pagination is by exclusion on the server: the client sends the set already on screen (Array.from(state.excluded), js:463), the WS receives excludecourseids (get_competency_links.php:60-65, PARAM_SEQUENCE, VALUE_DEFAULT) and the records query drops the courses already shown with AND c.id NOT IN (…) (get_in_or_equal(…, 'ex', false), :138-142) — the next page is the next unshown one, with no index to derive. Why this way: a numeric offset does not stay aligned when the list changes at both ends (picker and 🗑) — a newly added course's position depends on its fullname, which is the ordering key itself, so no client-side arithmetic fixes that case.
Both ends are idempotent. onAddCourse only counts when the id enters the set (if (!state.excluded.has(…)), js:754), so a double submit does not add twice; removeCourse mirrors it (if (!state.excluded.delete(…)) return, js:641) — the second unlink of a re-click resolves with success: false (unlink_competency_course.php:85) and lands on that guard. A state.loading flag discards a re-entrant "Load more" (js:451-453) and loadCourses skips a course already on screen when appending (js:478-480), closing the window of an add that lands in the middle of a fetch.
The ordering only stabilises the display. get_competency_links.php:151 orders by c.fullname ASC, c.id ASC; the tiebreak does not guard against skips/duplicates — the exclusion does that —, and the comment in the source says exactly that (:144-145). It is total because core's unique index courseidcompetencyid (competency_coursecomp) yields at most one row per course with the competencyid fixed in the WHERE. Two sibling WSes still order without a tiebreak — get_competency_courses.php:102 and search_linkable_courses.php:119, both ORDER BY c.fullname ASC only —, a latent follow-up not touched here.

What the screen does not demonstrate: here it is the CSS that swaps the chevron; in production it is a className in JS (js:572 / :580). The state is real; the swap mechanism is not.
The three header controls. The DOM order is [refresh][expand][restore][close], and only one of the expand/restore pair shows at a time.
• Expand/restore — central/modal_expander. attach (modal_expander.js:83-120) seeds the saved state synchronously, before the strings load (:90), and then inserts both buttons before the .btn-close (:98-99) — fa-expand and fa-compress, labels central_modal_expand / central_modal_restore (lang/en:199-200). The CSS is what chooses which one shows (styles.css:5255-5280), so nothing swaps an icon in JS. On click, if the activated button had focus, focus goes to the newly revealed twin (:106-118) — without that it would fall on the <body>, because the clicked button is exactly the one that hides itself.
• Refresh — central/modal_refresh. A single button (modal_refresh.js:36-48: .local-dimensions-modal-refresh, data-action="modal-refresh", <i class="fa fa-rotate">), anchored before the first .local-dimensions-modal-sizetoggle — or before the .btn-close if there is none (:67). On click it disables itself, spins the icon (fa-spin) and clears both in a finally (:80-83), so a reload that fails never leaves the button stuck. The label is core's string refresh (:63) — no new lang string.
• The wiring is one line: attachExpander(dialog).then(() => attachRefresh(dialog, …)) (js:909), and it is the chaining that guarantees the order. Here the refresh reloads the course list: reloadCourses (js:501-509) zeroes rowsEl / excluded / total and calls loadCourses for page 1 — a no-op while state.loading, so a reset never empties the list. Card expansion and loaded activities return to their initial state.
Click ⤢ above — the icon becomes ⤡ and the dialog widens; ⤡ brings it back. What the screen does NOT demonstrate: the shipped one is genuinely full screen — .modal-dialog.local-dimensions-modal-expanded gives width:100%; max-width:none; height:100%; margin:0 and the content loses its radius (styles.css:5288-5312). Here the width is a max-width tied to the preview panel, which does not run core/modal. And the width gain is not free to demonstrate: in this sample the activity name occupies one line in both states, so expanding undoes no wrapping — the real gain shows with a long name on a narrow screen.
The width has two mechanisms, and they stack. Modal.create opens with large: true (js:862), which is the base size; the class local-dimensions-modal-expanded overrides it with specificity 0,2,0 — with no !important and without Bootstrap 5's .modal-fullscreen, which 4.5 does not have (the reasoning is in the source itself, styles.css:5277-5280). The width is 100% and not 100vw on purpose: the parent .modal is position:fixed and its width already excludes the scrollbar column, so the dialog sits beside it instead of running underneath. The :has(.local-dimensions-modal-sizetoggle) also kills the container's second scrollbar (styles.css:5218-5224) and lets the title take the remaining width (:5015-5018).
The chosen size is a user preference, not a per-tab one. The expander reads and writes through HUB_STORE (modal_expander.js:39-42), which is the modalexpanded key of the hub's shared display (preferences.js:50 in the default, :113 getDisplay, :130 saveDisplay). The write goes to core_user/repository's setUserPreference with a 400 ms debounce (preferences.js:77-78, SAVE_DELAY at :36) — so the choice crosses sessions and devices, and it is the same in both modals that use the expander. The preference is declared in lib.php:143-149 (permissioncallback = \core_user::is_current_user) under the name in constants.php:90, and a caller from outside the hub must pass its own store (the parameter exists for exactly that, modal_expander.js:80-84) — otherwise a learner expanding a modal would write the administrative hub's preference.
The toast lives inside the modal, and this file is the reference case. js:914 calls addToastRegion(modal.getBody()[0]) on ModalEvents.shown (:911). The reason is z-index arithmetic: the page's .toast-wrapper is 1051 (theme/boost/scss/moodle/core.scss) and the dialog is 1055 ($zindex-modal, bootstrap/_variables.scss) — a toast fired from here would land behind the modal. Core's comment still says "above any modals": it aged in the jump to BS5, which raised the modal from 1050 to 1055. This is the modal that depends on it most: there are 5 addToast of its own (:652, :675, :710, :762, :927) plus the network one from notifyError, and none of those actions closes the dialog. Three of them also flash the element (flashRow, from central/flash.js:34-48, called at :674, :758 and :928): the toast says what, the flash says where. The flash reads its duration from the --mds-motion-flash token and is skipped entirely under prefers-reduced-motion (flash.js:38-40) — it is a redundant cue. The two without a flash are the removals: there is nothing to flash when the element has just left the DOM.
And what the removals get instead of the flash: focus. Leaving the DOM took focus along — it fell on the <body> and a keyboard user had to re-traverse the whole dialog. Both removals call restoreFocus (js:592-613), and each one prefers a different target. removeCourse (:651) goes to the chevron ([data-action="toggle-course"]) and not to the next 🗑: only the chevron is always rendered — the 🗑 is gated by capability, course by course. removeModule (:708-709) stays inside the card the user was in: it prefers the next activity's ✕ and falls back to that card's chevron when the last activity leaves. "Load more" takes precedence while it is visible (with a page pending, it is the way forward, not the picker). And the last resort is the autocomplete's enhanced input (SELECTORS.addInput, js:54), never state.addsel: core's enhance() hides the original <select>, and hidden it cannot take focus.
Why width is the scarce resource here. It is the hub modal with the most things per row: course name + short name + counter + 🗑, and inside it activity name + type + ✕ + outcome + badge + shared warning. The activity name wraps to two lines and then ellipsises (styles.css:7448-7463), with the whole name in the title (js:221).
Measurement note — in the rendered DOM, not on paper. This file's token decisions, with the number that supports each of them on both surfaces (DS light and DS dark):
• Control outline — the finding that is confirmed by measuring, not by reading. In the Moodle DS palette --border-strong and --border-stronger are the same literal (#ced4da in light, #6a737b in dark) and give 1.49:1 and 3.36:1 against the modal surface — they fail the 3:1 of 1.4.11 in light and scrape through in dark. --text-secondary passes on both, with 4.83:1 and 10.84:1 — and it is what .ctrl, .sel and .mtype use here.
• Text accent — the DS's dark --text-accent (#3f89cc) is measured in moodle-ds-alignment.md:184-200 at 4.37:1 and is kept there on purpose as a faithful portrait of Moodle; for the course name and "Load more" this screen uses its own --acc-fg (6.52:1 / 7.69:1).
• Danger — the course's 🗑 and the activity's ✕ land on the modal surface, never on a tint, so the DS's --text-danger serves directly: 5.29:1 and 5.91:1.
• What was NOT touched is on the record, with numbers: the tints stay low on purpose — what identifies these boxes is the border and the glyph, never the fill. The green badge and the toast give a fill of 1.32:1 in light and 1.14:1 in dark, while the border delivers 14.18:1 and 6.54:1; the alert and the shared warning, a fill of 1.13:1 and 1.83:1 with a border of 8.87:1 and 9.51:1; the header-control chip, a fill of 1.15 in light with the glyph at 7.53:1 in both themes, and the literals are the ones styles.css:5229-5272 and :5074-5103 publish. One detail of the DS palette that changes the ruler: --text-success and --border-success are the same literal in both themes, and --text-warning/--border-warning too — the distinction between them, which bites in palettes where they differ, does not exist here. .ctrl and .sel give a fill of 1:1 by definition: their background is the modal surface. The boxes (.card, .panel, .alist) stay on the kit's --border: they are containers, not controls.
• Measurement trap — it cost three wrong diagnoses, recorded here for the next screens. Switching the theme in a preview leaves any CSSTransition on color frozen: it stays at playState: "running" with currentTime: 0 forever, because the tab is not painting and nobody advances the clock, and getComputedStyle returns the colour of the previous theme. The ghost value looks like a real finding. Waiting does not fix it (the clock does not move) and injecting transition:none does not either — a new rule does not cancel a transition already under way. What does fix it is document.getAnimations().forEach(a => a.cancel()) before sampling. In this file the only elements with a transition on colour are the header controls, and their colours are fixed literals in both themes — the ghost does not appear here, but it appears in any screen whose transitioned value depends on the theme.
A finding that holds for the whole kit: --border-strong and --border-stronger do not work as a control outline in the Moodle DS palette — it is the same colour, and it fails in light. A control outline is --text-secondary.
