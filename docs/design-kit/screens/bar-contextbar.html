The bar's geometry, and where it comes from
(1) The bar aligns at the top. contextbar.mustache:58 is d-flex flex-wrap align-items-start gap-3 mb-4, so the labels "Context" (:66) and "Course category" (:83-85) sit on the same top line, and the category column can grow downwards without dragging the other one with it. (2) The toggle lives inside the context column. It is a div[data-region="hidden-cats"].mt-2 right below the System/Category btn-group (:75-79), rendering the shared partial local_dimensions/central/showhidden_toggle (:77) — the same one as EST/FWK/PLN. The two columns stay symmetrical: context gets the toggle, category gets the chip, both on the bottom line. (3) The selection chip sits below the field. That is CSS scoped over core's autocomplete: styles.css:7222-7225 stacks the [data-region='category-wrapper'] as a column and :7227-7230 puts order: 1 + margin-top: 0.25rem on the .form-autocomplete-selection, which core would render above the input. The counter (:94) and the Refresh (:101) carry an align-self-center of their own, and the ms-auto on the Refresh wrapper (:101) pushes it to the right edge.
The trap recorded in the CSS itself. The :not([hidden]) guard at styles.css:7222 is mandatory: the rule beats the browser's [hidden]{display:none}, and without it the category wrapper would show up in System mode (the comment at :7214-7221 describes exactly that, and asks for a re-check against the autocomplete's live DOM on every Moodle upgrade).
What the toggle and the field actually do
BAR-CATHIDDEN is client-side: context.js:335 re-calls enhanceCategory preserving the selected value and writes the preference (Preferences.saveNav({showhiddencats: …}), :336), with the change re-bound at :378; the key is sanitised at classes/helper.php:2311 and is born false in the navigation defaults (preferences.js:40). There is no reloadPane on that path — only the option list changes. BAR-CAT-01 is a <select class="form-select"> in the template (contextbar.mustache:86) that core turns into an autocomplete at run time (enhance, context.js:321) — which is why the CSS above has to target .form-autocomplete-selection and not an element of the plugin's own. The toggle's <label> is genuinely wrapping (showhidden_toggle.mustache:43-48), as Behat's "checkbox" named selector demands — an aria-label will not do.
In System mode the category column and the toggle disappear — both carry the same gate {{^iscoursecat}} hidden{{/iscoursecat}} (contextbar.mustache:76 and :82), and setContext follows the switch (context.js:250-253). What is left is Context + counter + Refresh.
The chip's number is not the counter's number
Each option's text is {{name}} ({{frameworkcount}}) (contextbar.mustache:89), so the selection chip always shows the structure count — including on the Plans tab. BAR-COUNT-01, on the other hand, follows the active mode: renderCounter (context.js:103-119) writes counts.plans when the mode is plans and counts.frameworks otherwise (:118), reading both from the selected option's data-frameworkcount/data-templatecount (selectedCounts, :80-96). Hence the drawing above: chip (7) structures, counter 4 plans, in the same category. The noun is explicit about the context — central_frameworks = "structures in this context" and central_plans = "plans in this context" (lang/{en,pt_br}/local_dimensions.php:126 and :226), in the two span[data-mode] of contextbar.mustache:97-98, of which renderCounter shows only the one for the active mode (:109-111). It declares that it counts the System/Category context, not the tab.
