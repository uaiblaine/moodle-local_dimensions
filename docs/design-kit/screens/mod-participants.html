Header — the three controls, and the order they arrive in
participants_manager.js:232 chains the two modules on one line: attachExpander(dialog).then(() => attachRefresh(dialog, refreshActiveTab)). The expander seeds the saved size synchronously (modal_expander.js:90, before the first await at :92), so the modal opens at the right size even with the refresh arriving afterwards. The refresh anchors itself before the first .local-dimensions-modal-sizetoggle (failing that, before the .btn-close) — modal_refresh.js:67-68 —, which gives the final order [refresh][expand][restore][close]. All four are the same chip of 1.75rem: combined base rule .local-dimensions-modal-sizetoggle, .local-dimensions-modal-refresh (styles.css:4929-4945), hover (:4947-4953), its own focus ring via :focus-visible (:4955-4959, no .btn), disabled (:4962-4964). The grouping with the close button comes from the rule .modal-header:has(.local-dimensions-modal-sizetoggle) .modal-title (styles.css:5015-5018), not from insertion order. Reach: the two modules are called in two of the hub's modals — this one and the courses-and-activities one (competency_links.js:909); the other modal-building points in amd/src/central/ get neither the refresh nor the expander. That is why the CSS is scoped by :has(.local-dimensions-modal-sizetoggle): the marker exists only in those two.

Width and the close chip
The dialogue receives two classes at once — modal-xl + local-dimensions-participants-modal (participants_manager.js:178-183). modal-xl is Bootstrap's own (800px at lg, 1140px at xl, identical in 4 and 5) and core's API only exposes setLarge(), hence the hand-set class; the plugin's own class hooks only the height rule (styles.css:4900-4902, full viewport height when there are autocomplete suggestions). There is no "modal with header links" class: the close chip arrives through the :has(.modal-body [class*='local-dimensions-']) arm because the body carries .local-dimensions-participants (comment at :180-181) — the old local-dimensions-headerlink-modal no longer exists (grep -rn headerlink over amd/, templates/, styles.css and classes/ returns zero). --bs-modal-width would not serve either: it was a BS5-only variable, and 4.5 defines no --bs-* custom property for the modal — the dialogue would fall back to 500px there.
styles.css:5074-5075 is a group of two selectors: the first (.modal:not(.local-dimensions-related-modal):has(.modal-body [class*='local-dimensions-']) .modal-header .btn-close) gives the chip to the modals whose body carries a plugin class — this is one of them; the second (.local-dimensions-central-page .modal-form-dialogue .modal-header .btn-close) covers the form modals (framework/competency/plan), whose core form body escapes the :has(). The .modal-form-dialogue core puts on the dialogue synchronously before show() pays for the chip from the first frame (025c2f6) — the class injected on LOADED arrived late and flashed. Literals with no dark variant: background #e7f0f9 (:5083), FA glyph \f00d in #0f4d85 (:5090-5095, 7.53:1 measured), hover #d4e6fb (:5098-5102, 6.82:1). The related-competencies modal is excluded on purpose (hidden header). And the overflow:hidden at :4916-4918 kills the second scrollbar — scoped precisely by :has(.local-dimensions-modal-sizetoggle), the marker that only this modal and the links one carry.
Footer — the admin links, revealed by core
The links live in the .modal-footer and it is core that reveals the footer by itself: show() only calls hideFooter() when it has no children (hasFooterContent = getFooter().children().length, in lib/amd/src/modal.js). The plugin exploits exactly that — injectFooterLinks (participants_manager.js:103-134) is awaited before show() (:185 → :296), so the group is already a child of the footer when core decides. Each destination is a btn btn-link p-0 + fa fa-external-link (:120-125) with target="_blank" + rel="noopener noreferrer" (:118-119), and the visible label is the accessible name — no extra title/aria-label (comment at :126). The group sits on the left through margin-right:auto on .local-dimensions-modal-footer-links (styles.css:5028-5034) — not through justify-content:space-between —, leaving any primary action (the framework form's Save/Cancel) on the right; the btn-link gets its own focus ring because BS4 zeroes its own (:5041-5045).

Lazy mounting — the latch, and the four panes' asymmetry
Three of the four panes are born empty in the Mustache and are mounted by JS; only the Users one arrives rendered from the server. modal.show() is :296; only afterwards does ModalEvents.shown (:233) fire startMount('cohorts', …) (:237) → mountCohorts, which still needs strings + renderForPromise + replaceNodeContents + a WS (cohort_manager.js:208-233). Because the Cohorts pane is born empty (participants_manager.mustache:75-76) and is the tab born active (:42), the modal opens with the four tabs drawn and a blank body under them. On a tab change, selectTab calls activateTab (:253) before ensureMounted (:256), so the pane sits visible and empty while the mount runs — true for Cohorts, Roles and Enrolment, the three <div></div>s. Users is the exception: it comes from the server (:77-144), so filters and table header appear at once and only the rows are missing.
The mount latch. A mounted table (:191) and a startMount(key, mountfn, selector) (:198-210) that claims the latch synchronously (:202 — a double click still fires one mount), stores each pane's {refresh} handle (:203-205) and releases the latch in the .catch (:207): the next activation of the tab tries again (ensureMounted, :243-248, which resolves the row in the MOUNTS table, :46-51). Cohorts is in the table, so re-clicking the default tab recovers too. Why it is safe (the invariant is written in the comment at :194-197): a released latch always means an unwired pane — Cohorts and Roles clear and rewire fresh children; Users and Enrolment only reject before the wiring goes in, because each one's single post-wiring failure is swallowed into a toast (participants_users.js:310, enrol_methods.js:1108) and therefore resolves the mount. Before c96a3e9 they were booleans raised before the await with a non-awaited mount: one rejection pinned the latch at true forever and, with setRemoveOnClose(true) (:172), the only way out was to close and reopen.
Hand-rolled tabs. No Bootstrap tab JS inside the modal (comment at :137): activateTab (:143-154) flips .active + aria-selected on the buttons (:145-148) and .show/.active on the panes (:149-153), with a WAI-ARIA roving tabindex on top (:263, maintained by selectTab at :255; Arrows/Home/End at :273-294). The toast region is hosted in the modal body (:236) so the managers' toast renders above the dialogue. Consequence: no existing waiting coverage reaches this modal — the hub's busy cover belongs to reloadPane (page tabs) and the tab-change loading belongs to core/dynamic_tabs (idem). There is nothing to inherit here.
