# S0: measures of the spikes (2026-11-23)

What stage S0 of `README.md` asked for, as measured. Stack m503b (Moodle 5.3, PHP 8.4, PostgreSQL), the
Browser pane visible on a 60 Hz display (16.4 ms a frame at rest, measured), signed in as an
administrator.

## The load framework

`spike/seed_s0load.php` (run with `docker exec -i m503b-webserver-1 php < seed_s0load.php`) created the
framework `S0LOAD` on m503b through core's API: 8 domains, 10 competencies in each, 24 indicators under
each competency, 2,008 competencies on three levels, a rule on 20 of them and 40 relations. It took
41.9 s. It stays on m503b (decision H11) under the short name "S0LOAD: 2,000 competencies (hub v2
spike)"; delete it from the hub's Structures tab when it is no longer wanted.

## (c) Large structure, before any change: React Flow 12.12.1 (main at d7ab013)

`hubv2.php?contexttype=system&frameworkid=4`, every branch opened by a script that clicks each expand
button in turn (88 clicks, each a `local_dimensions_browse_structure` call and a new layout).

| Measure | Value |
|---|---|
| Bundle | 221 KB transferred (the dev stack does not compress), 220 KB decoded |
| Nodes on the canvas, all open | 2,009 React Flow nodes, 2,008 edges, 28,687 DOM elements under the hub |
| One expansion, click to paint, round trip included | about 0.7 s at 250 to 1,000 nodes, 1.3 to 2.7 s from 1,500 nodes |
| Long tasks while opening everything | 113, the longest 362 ms, 13 above 200 ms, 13.4 s in total |
| JS heap, all open | 293 MB |
| Dragging the canvas, all open | 26 ms a frame on average (about 38 frames a second), 31 ms at the 95th percentile, 74 to 100 ms at worst |
| Selecting a node, all open | 81 ms to the second frame |

Reading: the canvas keeps every opened node in the DOM (`onlyRenderVisibleElements` is off), so the cost
grows with what was opened, not with what is on screen. It stays usable at 2,000 nodes and stops being
smooth from about 1,500.

## (a) React Flow 13.0.3 in the vendored build

Done in the worktree `~/dev/wt-local_dimensions-hubv2-s0`, branch `feat/hubv2-reactflow-13`, commit
`409d513`. What the upgrade cost:

- The vendored module grows from 186,376 to 250,133 bytes and the page's bundle from 225,658 to
  289,161 bytes (+63.5 KB minified, before compression). 13 brings `react-compiler-runtime` and
  zustand 5; exporting only the names the hub imports saves about 1.3 KB, so the size is the
  library's.
- Three source changes in the hub: `onNodesChange` receives a `NodeChangeset` read by type,
  `elevateEdgesOnSelect` is set back to false (13's default lifts the selected card's edges over the
  other cards), `FIT` is typed. `Nodes.tsx` and `graph.ts` are untouched.
- One stylesheet change: the pan cursor moves to the pane's `::before`, as 13's base rules do. 13's
  `color-scheme` and `light-dark()` rules are not ported, and 13 sets no colour class by itself, so the
  canvas still follows Moodle's `data-bs-theme` through the plugin's tokens.
- The build still needs the bridge that answers `require('react')`: zustand 5 no longer does it, but
  `react-compiler-runtime` is CommonJS. The output holds no runtime `require(`.
- In the page (the built bundle loaded over m503b's own with `spike/s0-helpers.js`): the tree draws
  as before, selecting a card fills the panel, the move mode starts, announces itself and Escape
  cancels it with the focus back on the card. No console error from the build.

## (c) again, both versions by one method

The session's Browser pane was hidden for the rest of the round, where frame times mean nothing. So
both builds were measured again by a method that does not depend on frames or timers
(`spike/s0-helpers.js`): long tasks while a script opens all 88 branches, then, with everything open,
the time to collapse and reopen three loaded branches and the synchronous cost of one viewport move.
Same page, same stack, minutes apart; the MacBook was running other sessions' gates the whole time,
so differences under about 20 % are noise.

| Measure, 2,009 nodes | React Flow 12.12.1 | React Flow 13.0.3 |
|---|---|---|
| Opening all 88 branches, sum of click-to-nodes times | 75.9 s | 82.5 s |
| The last ten expansions, average | 1,262 ms | 1,124 ms |
| Long tasks while opening: count, longest, above 200 ms, total | 101, 627 ms, 20, 14.9 s | 86, 1,644 ms, 21, 17.3 s |
| Collapse a branch of 250 nodes | 124 to 164 ms | 103 to 127 ms |
| Reopen it (already loaded) | 131 to 163 ms | 103 to 137 ms |
| One viewport move, script and forced layout | 4.98 ms on average, 15.3 ms at worst | 0.02 ms, 0.3 ms |
| JS heap | 183 MB | 195 MB |
| DOM elements under the hub | 28,633 | 28,537 |

Reading: 13 is not slower where it matters and is clearly cheaper to pan (it no longer renders React
on a viewport move, which is what cost 12 its frames). Its one 1.6 s long task is the first import
and compile of the sideloaded file. The cost of a large tree is the same in both: about 14 DOM
elements a node, all kept while opened.

Not measured: `onlyRenderVisibleElements`. A build with it on was made, but the script cannot open
what is not in the DOM, and the keyboard model of stage S2 needs the focused node in the DOM. It is
left for S2, together with focusing a branch (I4), which bounds the node count by design.

## (b) One Tab stop, arrow keys and tree roles inside React Flow 13

A spike in the worktree `~/dev/wt-local_dimensions-hubv2-a11y` (branch `spike/hubv2-a11y`, on top of
the React Flow 13 commit, never merged; stage S2 takes over what works). Its bundle was loaded over
m503b's own page and driven with real key presses.

| Target | Result | What decides it (React Flow 13.0.3 source) |
|---|---|---|
| One Tab stop | works: 1 stop for 9 nodes and for 19, where the page had 9 and 19 | `nodesFocusable={false}` removes the library's `tabIndex`, key handler, focus pan and default role (`NodeWrapper/index.tsx:58, 215-218`); `domAttributes` is spread last (`:222`), so our `tabIndex` and `aria-*` win |
| Arrow keys by structure | works: Tab enters at the framework, Right goes to "Domain 1", Right opens it (10 children load, focus stays), Right goes to "Competency 1.1", Down to "Competency 1.2", Enter selects it and the panel shows it; End, Home, the arrows and Space are consumed, Page Down and letters are left to the browser | a pure module, `keynav.ts`, over the tree's visible order, with 26 unit cases |
| A true ARIA tree on the canvas | not possible through the library's props | `ReactFlow/index.tsx:166` spreads the caller's props and then hard-codes `role="application"` (`:172`); that role sits between any tree we own and the nodes, which breaks ownership. `aria-owns` loses too: node wrappers take no `id` |
| Edges out of the accessibility tree | works: every edge carries `aria-hidden="true"` | `EdgeWrapper:213` spreads `domAttributes` after the role and the name |
| A named wrapper, descriptions reworded | works: the application is named with the framework's name | `aria-label` passes through the wrapper's spread |

The structure chosen for the canvas is therefore an `application` named after the framework, holding
`group` nodes whose names carry what a tree item's attributes would ("Domain 1, level 1, 1 of 8,
collapsed, 10 children, rule: all"), since `group` takes no `aria-level` or `aria-expanded`. The real
tree is the outline of stage S2, on the same selection, so a screen reader meets one tree, not two.
Idea I39 (own the drawing to get tree roles on the canvas) is not needed for that and stays closed.

Not settled by the spike, for S2 to prove in its own gate: where focus goes on fast key repeats (the
hidden pane delayed every event by about a second, so the trace above was read one key at a time),
the pan that keeps the focused node clear of the overview map on a short canvas, right-to-left, and
what VoiceOver and NVDA actually read for a node's name and its key help.
