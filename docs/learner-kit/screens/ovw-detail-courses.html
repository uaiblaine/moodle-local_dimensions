The pane has no heading of its own — the tab label names it and the count rides the tab. The whole card is the link to the course; there is no per-card Access button. A card carries a strong accent badge when the link's outcome is Completes the competency or Sends for review, and nothing otherwise. OVW-CRS-SINGLE · state strip replaces the progress bar card → course, "Go to activity" → the activity (two targets) drawer suppressed when it would repeat this activity
Same reasoning as the tracker's single-activity card, applied to a different component: there the timeline had no sequence to draw, here the percentage has only two values it can ever hold, so "0%" or "100%" is noise where the activity's own name and state are the answer. Drawn imageless like every compact card, its mark centred in a 56px box so it lands where the section card's ring lands, and the card carries a minimum height so losing the cover image does not leave it sitting short beside its image-bearing siblings. The mark and the "Completed / Not completed" line render only when the activity has completion tracking on; the activity's name always does. With two independent link targets: the outer <a> around the name, badge and state strip goes to the course; "Go to activity" is a second, separate <a> below it, to the activity itself — the card is not one anchor with a nested span. When the single activity is also the one the "N activities" drawer would list, the drawer is suppressed (matched by cmid, not by name) — otherwise the card shows the same activity twice. A locked or enrol state wins over this one: cardmode is only resolved server-side when access is open, so a gated card never names an activity the learner cannot reach.

OVW-CRS-SECTION · one qualifying section ^hasownname → name omitted (left card, "General"/"Topic 1") hasownname → name shown (right card)
The plan's mirror of the tracker's TRK-CARD-SECTION, from the same server call to calculator::resolve_card_shape() — the two views cannot disagree about a course's shape, but the number in the ring is not the same kind of number. calculator::describe_section() returns name, hasownname, url and tracked — no percentage — so the plan card shows the course-wide course.progress instead, the same field the ordinary bar reads; the tracker, by contrast, genuinely computes a per-section percentage. That reuse is sound rather than sloppy: with exactly one qualifying section, every trackable activity in the course sits inside it, so the course-wide figure and a section-scoped one would be the same number — the card reuses the figure it already has rather than computing a second one. A qualifying section counts whether or not it holds any modules (an empty section still takes this shape), so "one section" is the whole precondition, not "one section with several activities"; when nothing in it is tracked, section.tracked is false and no ring renders at all. The section's name renders only when a teacher authored one. Imageless and two-target like OVW-CRS-SINGLE above: the card links to the course, "Access content" links to /course/section.php. Both compact shapes put their mark centred in a 56px box, the same arrangement the tracker uses, and the card carries the same 220px floor. The ring is the tracker's own component reused — .local-dimensions-progress-ring-container plus -lg, r=12 in a 32-unit viewBox, arc = percentage × 0.754 — so the percentagedisplaymode setting reaches it without a rule of its own: fixed, on hover, or hidden, and hidden still leaves the arc, which a bare number could not. The resolver checks the activity shape first, so a course only ever lands here when it does not already resolve to a single activity — the two states are mutually exclusive, never both on the same card.

The filter runs server-side inside the courses web service, so it decides membership before any state is computed. The two settings are complementary, not redundant: the filter answers "should this card exist at all", the state answers "what can the learner do with it".
Data
One call to local_dimensions_get_competency_courses carries the whole pane. Per course it returns id, fullname, shortname, courseimage, progress, visible, ruleoutcome, the resolved access (open / enrol / locked), lockdate, isenrolstart, cardmode, the optional activity and section structures, and the activities list of the competency's module links inside that course. Because execute_returns is an allowlist, every one of those keys is declared there — anything not declared is silently stripped by clean_returnvalue, which is why the return structure and the payload are regression-covered together.
Pending · a subtle grey "Attach evidence" badge for OUTCOME_EVIDENCE. renderOutcomeBadge handles only OUTCOME_COMPLETE and OUTCOME_RECOMMEND and returns an empty string for everything else (accordion.js:1962-1964), and no outcome_evidence or outcome_none string exists in lang/en/local_dimensions.php — only outcome_complete (:515) and outcome_recommend (:516). The constants block states the reason (accordion.js:46-51): OUTCOME_EVIDENCE is core's DB default, so badging it would mark nearly every card instead of the few that decide anything.
Pending · activities whose course is not itself linked. There is no neutral-container card. get_linked_activities() is called with array_keys($courses) (get_competency_courses.php:121), and $courses comes only from competency_coursecomp (:98-103) after the enrolment filter (:115-127) — so a course carrying a linked module but no linked course produces no card, and its activities never reach the pane. Neither execute() nor renderCourseCardsScrollable has a branch for that case.
